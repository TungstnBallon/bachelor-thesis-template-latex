\section{Tabular data memory layout}
\label{section:column_vs_row}
When sequentially processing tabular data, a fundamental challenge arises: how to organize the two-dimensional data onto a linear layout, either on disk, or in memory.
Two primary approaches have been developed to address this challenge \autocite{Floratou2019}:
\begin{description}
	\item[row-oriented, row-storage] The values are saved one row after another.
	\item[columnar, column-storage] The values are saved column after column.
\end{description}

The earliest instances of columnar storage formats were initially developed for use in databases, with \emph{MonetDB} \autocite{Boncz2002} being a notable example.
By 2013 these formats had become widely implemented across the industry
\autocite{Abadi2013}.
In approximately 2011 initial research was conducted into the potential applications of columnar storage in the context of Big Data frameworks, which culminated in the development of \emph{Apache Parquet} and \emph{Apache ORC}, both disk-based columnar formats \autocite{Floratou2019}.

In 2016, The Apache Foundation initiated \emph{Apache Arrow}, which specifies a columnar storage layout \emph{in memory} \autocite{Ahmad2020}.

Columnar storage has advantages over row-oriented storage:
\begin{itemize}
	\item column specific compression \autocite{Abadi2013}
	\item less memory usage \autocite{Abadi2013}
	\item faster read times \autocite{Floratou2019}
\end{itemize}


\section{\emph{Apache Arrow}}
\label{section:arrow}
% "The \emph{Apache Arrow} project was initiated by the Apache Foundation in 2016.
% This framework provides an open and a common standardized format for different programming languages for reading/writing tabular data in-memory.
% Through language-specific libraries, multiple languages can share data without any copying or serialization." \autocite{Ahmad2020} (see \autoref{fig:arrow_com})
% "In the \emph{Arrow} format, data entries (records) are stored in a table called a RecordBatch.
% Each record field is stored in a separate column of the RecordBatch table in a manner that is as contiguous as possible in memory.
% This is called an \emph{Arrow} Array which can store data of different types — i.e., int, float, strings, binary, timestamps and lists, but also nested types (such as lists of lists, etc.).
% Arrays may have different types of physical buffers to store data.
% This layout provides higher spatial locality when iterating over column contiguous data entries for better CPU cache performance.
% SIMD (Single instruction, multiple data) vector operations can also benefit from such a layout as vector elements are already aligned properly in memory." \autocite{Ahmad2020}

\emph{Apache Arrow} is often used synonymously with the memory format it defines.
This format is \emph{language agnostic}, \emph{columnar} and \emph{in memory}.
It has implementations in many languages \autocite{arrow:overview} (see \autoref{subsubsection:arrow:langs} for a list).

In the \emph{Arrow} specification \autocite{arrow:spec}, a table is called \emph{record batch}.
They are comprised of \emph{Arrow} arrays which represent columns.
These \emph{Arrow} arrays are different from \emph{TypeScript} arrays, as they cannot contain different data types.
An \emph{Arrow} array's actual data is split across a series of \emph{Arrow} buffers, which represent continuous space in memory.
\emph{Arrow} record batches also have \emph{Arrow} schemas, which contain the batch's metadata.

\emph{Arrow} has a more granular type system than \emph{TypeScript}. This allows for a more precise control of memory.
\emph{Arrow} types can have parameters.
For example instead of \emph{TypeScript}'s type \Verb|number|, \emph{Arrow} has (un)signed integers with a bit width parameter,
decimals with width, scale and precision as parameters, and floating point numbers with a precision parameter.
The specification includes a physical memory layout for each type \autocite{arrow:spec}.

Additionally, the \emph{Arrow} specification defines an \ac{IPC} file format, that allows saving \emph{Arrow} record batches on disk.

At the time of writing this thesis, there are 48 projects powered by \emph{Apache Arrow} \autocite{arrow:projects}.

\section{\emph{Polars}}
\label{section:polars}
\emph{Polars} is built on top of the \emph{Rust} implementation of the \emph{Arrow} specification.
It incorporates convenient abstractions such as \Verb|DataFrame| and \Verb|Series|.
Additionally, it uses \emph{NAPI-RS} to provide a \emph{TypeScript} \ac{API} that preserves the performance of the \emph{Rust} library.
It promises "up to 50x performance" \autocite{polars}.
