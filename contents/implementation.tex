In this chapter, we explain the implementation of the architecture described in \autoref{chapter:Architecture}.
In instances where this thesis makes reference to filenames, the corresponding path can be found in \autoref{tab:src}.

In general, we prefer methods, such as \Verb|map(...)|, over for loops, because they are, in our experience, less error-prone and result in more readable code.

\section{Type Conversion}
\label{subsection:TypeConversion}
As described in \autoref{section:type_conversion}, we implement a conversion mechanism between Polars' DataTypes and Jayvee's ValueTypes.

\subsection{Conversion from DataType to ValueType}
\label{impl:types:dtov}
The class \Verb|ValueTypeProvider|, located in \Verb|primitive-value-type-provider.ts|, implements this method:
\begin{center}
	\begin{minted}{typescript}
	fromPolarsDType(dtype: polars.DataType): ValueType
	\end{minted}
\end{center}
It uses the method \Verb|DataType.equals(...)| instead of \Verb|===| for a more accurate comparison of DataTypes.
- uses if instead of switch-case to make it clear that this is equals instead of ===
The Polars type system is more granular than that of Jayvee, which results in the occurrence of DataTypes, that yield the same ValueType.
For instance, both \Verb|polars.Float32| and \Verb|polars.Float64| return \Verb|Decimal|.

\subsection{Conversion from ValueType to DataType}
The interface \Verb|ValueType|, located in \Verb|value-type.ts|, defines this method:
\begin{center}
	\begin{minted}{typescript}
	toPolarsDataType(): polars.DataType | undefined
	\end{minted}
\end{center}
is defined in the interface \Verb|ValueType| interface.
The classes representing ValueTypes, that are not supported by Polars, implement this method to return \Verb|undefined|.

\subsection{InternalValueRepresentation}
In many cases, the return type of Polars methods, that return concrete values, is \Verb|any|.
However, the Jayvee interpreter expects such a value to have the type \Verb|InternalValueRepresentation|.
To narrow down the returned type \Verb|any|, we expand the existing type guards, implemented in \Verb|typeguards.ts|, to handle inputs with the type \Verb|unknown|.
\autoref{tab:internalvaluerepresentation} contains a list of internal types and the mechanism their type guard uses.

\subsubsection{PolarsTableInterpreterExecutor}
\label{subsubsection:polarstableinterpreterexecutor}
The static attribute \Verb|type| is set to \Verb|'PolarsTableInterpreter'|.
The method \Verb|getExecutorForBlockType(...)| compares this attribute to the blocktype from the jayvee source file.
As a consequence of the alterations, made to the block executor selection process in \autoref{subsection:createBlockExecutor}, the interpreter is now searching for the \Verb|PolarsTableInterpreter| instead of \Verb|TableInterpreter|, if the \Verb|--use-polars| command line interface \ac{CLI} flag is enabled.

\Verb|PolarsTableInterpreterExecutor|'s objective is, to transform the existing, row-oriented, \ac{CSV} data into a columnar table format.
This is addressed by iterating over all rows multiple times, with each iteration constructing only one column (see \autoref{lst:polarsTableInterpreter:constructSeries}).
This process yields a list of Polars \Verb|Series|, which are then utilized to construct a columnar Polars DataFrame.

The method \Verb|constructAndValidateTable(...)| skips the first row of the input data, if the block property \Verb|header| is set to \Verb|true|.
The use of the ternary if statement is justified by the fact that, it allows \Verb|rows| to be declared as a constant.

\begin{listing}
	\begin{minted}{python}
def constructAndValidateTable(sheet, header, columnEntries, context):
	rows = sheet.getData()
	# rows is a row-oriented, two dimensional array of strings
	if header:
		... # Skip first row
	series = []  # Empty list
	for entry in columnEntries:
		s = this.constructSeries(rows, entry, context)
		series.add(s)
	dataFrame = polars.DataFrame(series)
	return new PolarsTable(dataFrame, context.valueTypeProvider)
	\end{minted}

	\label{lst:polarsTableInterpreter:constructTable}
\end{listing}

\section{FileToTableIntepreter}
The block type definition located at \Verb|FileToTableInterpreter.jv| defines the following properties:
As the block type \Verb|FileToTableInterpreter| is a combination of \Verb|TextFileInterpreter|, \Verb|CSVInterpreter| and \Verb|TableInterpreter|, their properties and default values are incorporated into the definition.
One property, \Verb|TextFileInterpreter|'s \Verb|lineBreak|, is no longer supported, due to the fact, that line splitting is handled by Polars, which does not support line breaks based on a \ac{regex}.

\subsection{FileToTableIntepreterExecutor}
The block executor \Verb|FileToTableInterpreterExecutor| is implemented in \Verb|file-to-table-interpreter-executor.ts|.

Given the close relationship between the block \Verb|FileToTableInterpreter| and \Verb|TableInterpreter| (see \autoref{subsection:FileToTableInterpreter}), it is reasonable to share code with \Verb|TableInterpreterExecutor|, in order to enhance both consistency and maintainability.
Specifically, the method \Verb|TableInterpreterExecutor.deriveColumnDefinitionEntriesWithoutHeader(...)| and the function \Verb|toPolarsDataTypeWithLogs| were reused.

Polars only supports the \ac{UTF-8} encoding, with the option to either crashing when an error occurs, or incorrectly decoding the text.
This is different from the original implementation, which supports more encodings.
Because this block's objective is to let Polars handle text parsing, this is also a limitation of the block type \Verb|FileToTableInterpreter|.
Given that this is a new block type, we do not consider this limitation to violate the \emph{compatibility} requirement.

The method \Verb|doExecute(...)| is deemed sufficiently straightforward, to not need a separate method, such as \Verb|TableInterpreterExecutor.constructAndValidateTable(...)|.


\subsection{LocalFileToTableExtractor}
As described in \autoref{arch:execs:localfiletotableextractor}, the block type \Verb|LocalFileToTableExtractor| is based on \Verb|FileToTableInterpreter|.
As a consequence, the block type definition, located in \Verb|LocalFileToTableExtractor.jv| includes all of \Verb|FileToTableInterpreter|'s properties.

The class \Verb|LocalFileToTableExtractorExecutor|, implemented in \Verb|local-file-to-table-extractor-executor.ts|, reuses the method \Verb|csvOptions(...)| from the class \Verb|FileToTableInterpreterExectutor|.

It is not feasible to share code with \Verb|LocalFileExtractorExecutor|, because the TypeScript compiler identifies a circular dependency.
As a result, the method \Verb|doExecute(...)| has to reimplement a check preventing upward path traversal.

\subsubsection{Operator evaluators}
\label{subsubsection:impl:operator_evaluator}
\autoref{tab:impl:expressions} contains a table linking every Jayvee operator evaluator with the Polars expression it evaluates to.
Many Jayvee operators have an equivalent Polars expressions.

Polars does not have an \Verb|xor| expression, but the \Verb|and|, \Verb|or| and \Verb|not| expressions can be used to create a logically equivalent expression.

Jayvee's \Verb|sqrt| is transformed to the mathematically equivalent \Verb|pow(1/2)|.

Polars \Verb|round| expression expects the number of digits after the comma as a parameter.
We pass \Verb|0|, to remain consistent with the TypeScript implementation.

\Verb|root| and \Verb|pow| are unsupported, because Polars' \Verb|pow| expression expects a constant exponent.

\Verb|replace| and \Verb|matches| are unsupported.
Polars has expressions that allow working with \ac{regex}s, the time frame was too short to figure out a solution.

Polars allows users to parse strings, by casting them to a target Polars DataType \autocite{polars:docs:expr:parsing}.
\Verb|asText|, \Verb|asDecimal| and \Verb|asInteger| convert their respective Jayvee ValueType to obtain this target DataType. \\
\Verb|asText|, \Verb|asDecimal| and \Verb|asInteger| are implemented this way. \\
Polars does not allow casting strings to booleans \autocite{polars:docs:expr:parsing}, which means that the \Verb|asBoolean| operator is unsupported.

\section{SQLiteLoaderExecutor}
\Verb|SQLiteLoaderExecutor| is implemented in \Verb|libs/extensions/rdbms/exec/src/lib/sqlite-loader-executor.ts|.

\Verb|doExecute| retrieves and validates the blocks properties: \Verb|file|, \Verb|table| and \Verb|dropTable|, which are passed to the \Verb|executeLoad| method.

\Verb|executeLoad| provides a general implementation that works for \Verb|TsTable| and \Verb|PolarsTable|, because it uses the abstract \Verb|Table| class' methods to generate \ac{SQL} queries.
These methods are \Verb|generateDropTableStatement|, \Verb|generateCreateTableStatement| and \Verb|generateInsertValuesStatement|.

\Verb|PolarsSQLiteLoaderExecutor| and \Verb|TsSQLiteLoaderExecutor| don't override the default implementation.

\Verb|RustSQLiteLoaderExecutor| overrides \Verb|executeLoad|.
Its implementation writes the table to \Verb|dataframe.arrow| (the .arrow extension is recommended by the Arrow specification \autocite{arrow:spec}), using \Verb|PolarsTable|'s \Verb|writeIpcTo| method.
Then it calls the \Verb|loadSQLite| function implemented in \Verb|sqlite-loader-lib|.
