\chapter{Architecture}
\label{chapter:Architecture}

The objective of this thesis is to optimize \emph{Jayvee}'s internal data representation.
This necessitates modifying the \emph{Jayvee} interpreter, the program, that parses \emph{Jayvee} source files and executes the defined pipelines.

In order to improve the class diagrams' readability, some parameters and return types have been abbreviated with "\dots".

\section{Interpreter Overview}
\label{section:prev}

This section provides an overview of how the interpreter executes a \emph{Jayvee} pipeline and the involved classes, illustrated by \autoref{fig:uml:overview}.
How the interpreter parses a \emph{Jayvee} source file is not relevant for the purpose of this thesis.

Once the parsing process is complete, the interpreter obtains a series of pipeline definitions, which consist of block definitions.
Block definitions include a \emph{block type}.
The interpreter uses this block type to find an executor for the block, which is a class that implements the interface \Verb|BlockExecutor|.
The interpreter then executes these executors in the order specified in the pipeline definition.
The output of the preceding block executor is always the input for the subsequent one.

Inputs and outputs are instances of classes that implement the interface \Verb[breakbefore=TIt]|IOTypeImplementation|.
This includes the \Verb|Table| class, which will be used to integrate \emph{Apache Arrow} into the \emph{Jayvee} interpreter.

One of \emph{Jayvee}'s core features is the transformation of tables with the \Verb|TableTransformer| block type.
Consequently, we will devote particular attention to this functionality.
The executor for blocks of type \Verb|TableTransformer| is \Verb|TableTransformerExecutor|.
It creates and executes the \Verb|TransformExecutor|, which evaluates the transform's expression for every row of the table and returns the resulting column.
This column is then added to the input table by \Verb|TableTransformerExecutor|

Expressions are evaluated by the function \Verb|evaluateExpression(...)|.
Expressions with parameter(s) (unary, binary, ternary) are called operators.
They have evaluator classes that implement the interface \Verb|OperatorEvaluator|.
The function \Verb|evaluateExpression(...)| finds the correct evaluator with the help of the \Verb|OperatorEvaluatorRegistry|.

\section{General approach}
\label{section:General Idea}
We add an alternative table implementation, based on the \emph{Apache Arrow} framework (\autoref{section:arrow}), to the interpreter.
This means, the interpreter will contain two table implementations at the same time.
\textcite{Dooley2024} recommend the strategy pattern for this situation, because it will ensure that both implementations share a common interface and that the different implementations can be chosen dynamically.

We also adapt the interpreter to take advantage of the new features introduced by the new table (see \autoref{fig:interpreter_activity}).
But, because the original implementation needs to be preserved here too, the strategy pattern is a good approach again.

\subsection{Possible implementations of \emph{Arrow}}
\label{subsection:arrow implementations}

\subsubsection{Implementation from scratch}
\label{subsubsection:direct_implementation}
The most direct approach would be a new implementation of the \emph{Arrow} specification.
This would afford the advantage of having full control over the implementation.

However, it is not guaranteed, that a sufficient amount can be implemented within the timeframe of the thesis.
Furthermore, this implementation may not perform as well as an existing, more mature implementation, which may also be more correct.

\subsubsection{\emph{Apache Arrow} in \emph{TypeScript}}
\label{subsubsection:arrow_in_js}
There is an \emph{Arrow} library written in \emph{TypeScript} \autocite{arrow:overview}, which is the language of the \emph{Jayvee} interpreter.
This implementation is comparable to those in other languages regarding supported data types, but it lags behind with support for other Apache frameworks \autocite{arrow:status}, which takes away one of \emph{Arrow}'s strengths.

\subsubsection{\emph{Polars}}
As described in \autoref{section:polars}, \emph{Polars} is a high level library built on top of \emph{Apache Arrow}, which also offers useful abstractions such as \Verb|DataFrames|, that hide the \emph{Arrow} data types.
These abstractions make it easier for developers unfamiliar with \emph{Arrow} to contribute to \emph{Jayvee}.

\emph{Polars} is written in \emph{Rust}, but offers a \emph{TypeScript} \ac{API}, which enables the \emph{Jayvee} interpreter to use \emph{Polars}.
For these reasons, we choose to build the new table implementation on top of \emph{Polars}.



\section{Type conversion}
\label{section:type_conversion}
\emph{Jayvee} types, e.g. text, boolean or decimal \autocite{jvalue:jayvee:docs:core_concepts}, are represented by the interface \Verb|ValueType|,
They are useful, because \emph{Jayvee} types do not map directly to \emph{TypeScript} types.
For example, when a value inside a table has the \emph{TypeScript} type \Verb|number|, an object implementing the interface \Verb|ValueType| denotes, whether the value is a \emph{Jayvee} \Verb|integer| or a \emph{Jayvee} \Verb|decimal|.

\emph{Polars}' types are represented by the class \Verb|DataType|.
The class \Verb|DataType| is not compatible with the interface \Verb|ValueType|, which leaves us with two possible approaches.
\begin{description}
	\item[Replace] \Verb|ValueType| with \Verb|DataType|.
	      We decided against this approach, because it enforces the \emph{Polars} implementation at compile time, which breaks the \emph{feature toggle} requirement.
	\item[Convert] between \Verb|ValueType| and \Verb|DataType| when needed.
	      The \emph{TypeScript} implementation can ignore the conversion and keep using \Verb|ValueType| as before.
	      Because of the \emph{feature toggle} requirement, we choose this approach.
\end{description}



For details on how this conversion mechanism is implemented, see \autoref{subsection:TypeConversion}.

\section{Creating a table implementation based on \emph{Polars}}
\label{section:new_table}

The usual application of the strategy pattern would create an interface \autocite{Dooley2024} that both the old and the new table classes implement.
Instead, we utilize an abstract class, to allow for code-sharing between the table subclasses.
We can still define functionality for both subclasses using \emph{abstract methods}.

\emph{Jayvee} already contains a class \Verb|Table| that implements the interface \Verb|IOTypeImplementation<IOType.TABLE>|.
We move all the functionality from \Verb{Table} to the class \Verb{TsTable} and create a new abstract class \Verb|Table|.

\subsection{Table}
This class implements the interface \Verb|IOTypeImplementation<IOType.TABLE>| to be allowed as an input or output for blocks.
Its methods are based on those of the original class \Verb|Table|.
See \autoref{fig:uml:table} for a class diagram.

\subsubsection{Differences between the old class Table and the new abstract class Table}
The methods \Verb|getRow(...)|, \Verb|addRow(...)|, \Verb|dropRow(...)| and \Verb|dropRows(...)| are not part of the abstract class \Verb|Table|.
These methods work with rows, so their usage would make the columnar data representation obsolete.
They still exist in the \Verb|TsTable| class to satisfy the \emph{compatibility} requirement.

In order to meet the requirement \emph{feature toggle}, it is necessary to distinguish the concrete table implementation.
Therefore, we have implemented the type guards \Verb|isPolars()| and \Verb|isTypescript()|.

Given the difficulties in executing operations with side effects in parallel \autocite{Gordon2012}, it is preferable to clone tables rather than mutate them.
To satisfy the compatibility requirement, a new method, \Verb|withColumn(...)| is created to implement this behavior.
The method \Verb|TsTable.addColumn(...)| preserves the old behavior.

Because of the fact, that the \emph{Polars} and \emph{TypeScript} implementations of the method \Verb|generateDropTableStatement(...)| are identical, we implement it as a non-abstract method in \Verb|Table|.

\subsection{PolarsTable}
\label{subsection:arch:polarstable}
\emph{Polars}' \Verb|DataFrame| already has table functionality, such as the ability to add, remove and transform columns.
However, \Verb|DataFrame|'s methods aren't the same as those required by \Verb|Table|.
To solve this, we create a wrapper class \Verb|PolarsTable|, that extends \Verb|Table| and thereby implements \Verb[breakbefore=T,breakafter=<]|IOTypeImplementation<IOType.TABLE>|, allowing \Verb|PolarsTable| to be used as an input or output for block executors.

\Verb|PolarsTable| extends \Verb|Table|'s abstract methods by calling \Verb|DataFrames| methods, which is a characteristic of the \emph{adapter pattern} \autocite{Dooley2024}.
In the terminology of the adapter pattern, \Verb|Table| is the target, \Verb|PolarsTable| the adapter and \Verb|DataFrame| the adaptee.

It is notable, that when \Verb|Table| is parameter or return type in an abstract method in \Verb|Table|, the overriding method in \Verb|PolarsTable| replaced that with \Verb|PolarsTable|.
For example, %FIXME ensure this looks good
\mint{typescript}{abstract clone(): Table}
becomes
\mint{typescript}{override clone(): PolarsTable}

\subsubsection{New functionality enabled by \emph{Polars}}
In addition to the abstract methods from \Verb|Table|, \Verb|PolarsTable| also implements methods that take advantage of \emph{Polars}' features unavailable to the \emph{TypeScript} implementation.

The method \Verb|withColumn(...)| is overloaded with a second signature, that can handle \emph{Polars} expressions.
\emph{Polars} expressions are a way to describe a series of operations, that result in one or more columns, with automatic optimization and parallelization \autocite{polars:docs:expr}.
\autoref{lst:pl_expr_example} contains an example of how \emph{Polars} expressions can be chained.
\begin{listing}[h]
	\begin{center}
		\begin{minted}{typescript}
use { pl } from 'nodejs-polars';
// Creation of the DataFrame was omitted
const dataFrame = ...;
// When the expression is applied to a DataFrame, `pl.col(...)` selects a column, based on the name
const first = pl.col("a")
const second = pl.col("b")
// When the expression is applied, `mul` multplies all values from expression `first` with those from `second`
const product = first.mul(second)
// When the expression is applied, `alias("c")` renames the column to "c".
const renamed = product.alias("c");
// withColumn applies the expression and returns a DataFrame, containing the column computed by the expression.
const newDataFrame = dataFrame.withColumn(renamed)
// `newDataFrame` contains a column "c". "c" contains the values of column "a" multplied with the values from column "b"
	\end{minted}
	\end{center}
	\caption{Multiplying the values in the columns "a" and "b" of a \Verb{DataFrame}.}
	\label{lst:pl_expr_example}
\end{listing}

The methods \Verb|writeIpc(...)| and \Verb|writeIpcTo(...)| convert the table to the \emph{Arrow} \ac{IPC} format, writing either into a buffer or a file.

One of the challenges is, that adding a column into a \Verb|DataFrame| object loses that column's \Verb|ValueType|, because the \Verb|DataFrame| uses \emph{Polars}' \Verb|DataType|.
This is problematic, because the class \Verb|TableColumn| expects a \Verb|ValueType| for its constructor.

The solution is to convert the \emph{Polars} \Verb|DataType| object into a \Verb|ValueType| object using the conversion mechanism in \autoref{subsection:TypeConversion}.
This conversion requires a \Verb|ValueTypeProvider| object, which is saved as one of \Verb|PolarsTable|'s properties.
Refer to \autoref{fig:uml:polarstable} for the class diagram.

\subsubsection{PolarsTableColumn}
The method \Verb|DataFrame.getColumn(...)| returns an instance of the \emph{Polars} class \Verb|Series|, which means that \Verb[breakbefore=o]|Series| represents a column in \emph{Polars}.
To make \Verb[breakbefore=o]|Series| useful, we create a class adapter with the target \Verb|TableColumn| and the adaptee \Verb|Series|.

One challenge here is, that \Verb|Series| does not have a generic type parameter.
This limitation can be addressed in two ways:
\begin{itemize}
	\item Create the class \Verb|PolarsTableColumn| without a type parameter and extend the abstract class \Verb|TableColumn<InternalValueRepresentation>|.
	\item Create the class \Verb[breakanywhere]|PolarsTableColumn<T>| with a type parameter and extend the abstract class \Verb|TableColumn<T>|.
\end{itemize}

The second approach is preferable, because it allows us to preserve the generic type parameter of the property \Verb|_valueType: ValueType<T>| (see \autoref{fig:uml:polarstablecolumn}).

It should be noted, that \Verb|T| does not indicate the actual type of the values stored in the column, as would be the case for \Verb|Array<T>|.
This detail is left to \Verb|Series|.
\Verb|T| specifies what type the column's values would be, if it were implemented in \emph{TypeScript}.
This is used to narrow down the type of \Verb|_valueType|.

\subsection{TableInterpreter}
The block type \Verb|TableInterpreter| converts a Sheet, \emph{Jayvee}'s representation for \ac{CSV} data, into a table.
We create an abstract class \Verb|TableInterpreterExecutor| that extends \Verb|AbstractTableInterpreter<IOType.SHEET, IOType.TABLE>| (\autoref{fig:uml:tableinterpreter}).
For implementation details, see \autoref{section:tableinterpreterexecutor}.
\Verb|TableInterpreter| has two subclasses, \Verb|TsTableInterpreter|, which contains the old behavior, and the new \Verb|PolarsTableInterpreter|.

This architecture, like the table architecture in \autoref{section:new_table}, follows the strategy pattern from \textcite{Dooley2024}.
The usual strategy interface is split up into \Verb|BlockExecutor|, \Verb|AbstractBlockExecutor| and \Verb|TableInterpreterExecutor|, while the concrete strategy is either \Verb|TsTableInterpreterExecutor| or \Verb[breakbefore=TIEpt]|PolarsTableInterpreterExecutor|.

In order to facilitate code sharing, we use static methods to implement behavior that is useful for other executors as well.

\begin{figure}
	\begin{plantuml}
		@startuml
		hide empty members

\subsection{FileToTableInterpreter}
\label{subsection:FileToTableInterpreter}
Blocks with the type \Verb|FileToTableInterpreter| receive a \Verb|BinaryFile|, which contains a \emph{TypeScript} \Verb|ArrayBuffer| and converts that into a table.
This combines the block types \Verb|TextFileInterpreter|, \Verb|CSVInterpreter| and \Verb|TableInterpreter|.

Merging these block types allows us to utilize \emph{Polars}' builtin \ac{CSV} parsing functionality, instead of relying on the \Verb|fast-csv| library, like \Verb|CSVInterpreter|, which means less indirection when reading a \ac{CSV} file.

\subsubsection{Adding a block type}
To add this block type to the \emph{Jayvee} language, its definition is put in the file \Verb|FileToTableInterpreter.jv| (refer to \autoref{tab:src} for the full path).
Running the command \Verb|npm run generate| creates class definitions necessary for this block type to be used in the \emph{Jayvee} interpreter.

We also create an executor for the new block type (\autoref {fig:uml:filetotableinterpreter}).
All methods except \Verb|doExecute(...)| are static, making them reusable by other executors.

In practice, the only executor using these, is \Verb|LocalFileToTableExtractorExecutor|.
Because there is no preexisting implementation of this executor, we do not need an additional abstract class and can extend \Verb|AbstractBlockExecutor| directly.

\subsection{SQLiteLoaderExecutor}
\emph{Jayvee} blocks with type \Verb|SQLiteLoader| load their input table into a \emph{SQLite} database.
Its output \Verb|IOType| is \Verb|None|, so no blocks in the pipeline can come after a block with type SQLiteLoader.
The abstract \Verb|SQLiteLoaderExecutor| (\autoref{fig:uml:sqliteloader}) offers a general implementation, utilizing methods defined in the abstract \Verb|Table| class.
This approach includes serializing all the data contained in the input table into a \ac{SQL} query with type string.
We consider this to be a non-optimal representation of the data and improve it in \autoref{arch:sqlite:lib}.

\Verb|SQLiteLoaderExecutor| has three subclasses:
\Verb|TsSQLiteLoaderExecutor| doesn't override the super class' methods to preserve the original \emph{TypeScript} implementation.
\Verb|PolarSQLiteLoaderExecutor| doesn't override the super class' methods, because \emph{Polars}' \emph{NodeJS} \ac{API} does not offer any database functionality at the time of writing this thesis.
The different behavior results from different overrides of the methods \Verb|generateCreateTableStatement| and \Verb|generateInsertValuesStatement| in the classes \Verb|PolarsTable| and \Verb|TsTable|.

\subsubsection{RustSQLiteLoaderExecutor}
\Verb|RustSQLiteLoaderExecutor| avoids serializing the input table's data into a \ac{SQL} query string, by relying on an external library, \emph{sqlite-loader-lib}.

\subsection{\emph{sqlite-loader-lib}}
\label{arch:sqlite:lib}
\emph{Polars}' core functionality is written in \emph{Rust}, which \textcite{polars} describe as allowing "for high performance with fine-grained control over memory".
For this reason, we choose \emph{Rust} to implement \emph{sqlite-loader-lib} (see \autoref{fig:uml:rust_components}).

	\caption{The \emph{Rust} components used by the interpreter.}
	\label{fig:uml:rust_components}
\end{figure}

\emph{Polars} uses \emph{NAPI-RS} \autocite{polars:src:napi}, which compiles a \emph{Rust} library to a \emph{NodeJS} addon \autocite{napi}.
With this, the \emph{Jayvee} interpreter, written in \emph{TypeScript}, can use functions from a library written in \emph{Rust}.

We were not able to pass the table to the library as a function parameter.
This would require redefining the class \Verb|PolarsTable| inside \emph{sqlite-loader-lib} using \emph{NAPI-RS}.
Instead, the class \Verb|RustSQLiteLoaderExecutor| saves its input table into an \emph{Arrow} \ac{IPC} file on disk.
\emph{sqlite-loader-lib} can then read this file and reconstruct the table.


Because the library only exists to execute a single task, it only exposes one function:
\mint{typescript}{loadSqlite(ipcPath: string, tableName: string, sqlitePath: string, dropTable: boolean): void}
Its parameters are the path of the \emph{Arrow} \ac{IPC} file and the properties of the \Verb|SQLiteLoader| block.

At the time of writing this thesis, \emph{Polars}' \emph{Rust} implementation doesn't offer database export either.
As a consequence, \emph{sqlite-loader-lib} uses a separate library to interface with a \emph{SQLite} database.
This library, known as \emph{Connector Arrow}, enables the writing of \emph{Arrow} record batches into a \emph{SQLite} database table \autocite{connector-arrow}.
Connector \emph{Arrow} relies on the \emph{rusqlite} library to support \emph{SQLite} databases \autocite{connector-arrow}.

See \autoref{subsection:sqlite-loader-lib} for the implementation.

\section{Transforms}
\label{section:transforms}
The \Verb|TableTransfromerExecutor| class creates an instance of a concrete subclass of \Verb|TransformExecutor| to compute a new column for it's input table.
For \Verb|PolarsTableTransformerExecutor| this is an instance of  \Verb|PolarsTransformExecutor| (\autoref{fig:uml:transformexecutor}), for \Verb|TsTableTransformerExecutor| this is \Verb|TsTransformExecutor|.
% Then, that instance's \Verb|executeTransform| method is called, which returns either the new column or an expression to compute the new column.

Originally, \Verb|TransformExecutor| would compute the new column by following the algorithm outlined in \autoref{lst:old_eval}.
\begin{listing}[h]
	\begin{center}
		\begin{minted}{python}
newColumn = ...  # An empty column
expression = transform.expression
for row in inputColumns:
	...  # add row to evaluation context
	let value = evaluateExpression(expression, context)
	newColumn.add(newColumn)
	...  # remove row from evaluation context
return newColumn
	\end{minted}
	\end{center}
	\caption{Pseudocode of the old algorithm the interpreter used, to execute transforms.}
	\label{lst:old_eval}
\end{listing}
It applies the \emph{Jayvee} expression to each row in the input columns and returns a column.

The new approach transforms the \emph{Jayvee} expression into a \emph{Polars} expression, that the \Verb|PolarsTableTransformer| can apply to its input table.
So, we add the new function \Verb|jayveeExpressionToPolars(...)| (see \autoref{section:expressions}), which is similar to the existing \Verb|evaluateExpression(...)|, but it returns a \emph{Polars} expression, not a final value.

A detailed explanation of this process can be found at \autoref{section:impl:transforms}.

\section{Expressions}
\label{section:expressions}
\textcite{polars:docs:expr} separate \emph{Jayvee} expressions into three categories: \emph{literals}, \emph{variables}, \emph{operators}.
\begin{description}
	\item[literal] Concrete values, e.g. \Verb|5|, \Verb|"sometext"| or \Verb|true|.
	      Their evaluation does not differ from the original implementation.
	\item[variable] Represents a value defined in the evaluation context (\autoref{fig:uml:eval_context}).
	      Variables are used to refer to columns inside of transforms.
	\item[operator] Transforms one to three \emph{Jayvee} expressions into one result.
	      The evaluation context contains a registry of operator evaluators (see \autoref{subsection:arch:operator_evaluators})
\end{description}
\emph{Jayvee} expressions are transformed to \emph{Polars} expressions using the function \Verb|jayveeExpressionToPolars(...)| (see \autoref{impl:expressions}).

\subsection{Operator evaluators}
\label{subsection:arch:operator_evaluators}
Evaluators implement the interface \Verb|OperatorEvaluator|.

We create a new interface \Verb|PolarsOperatorEvaluator|, that defines one method, \Verb|polarsEvaluate(...)| and extends the existing \Verb|OperatorEvaluator|.
As a consequence, all classes that implement \Verb|PolarsOperatorEvaluator| are also required to implement the properties defined by \Verb|OperatorEvaluator|.
This ensures, that the existing \emph{TypeScript} implementation remains available.

All classes, that previously implemented \Verb|OperatorEvaluator| interface, now implement \Verb|PolarsOperatorEvaluator| (see \autoref{subsubsection:impl:operator_evaluator}).

We deliberately did not follow the strategy pattern approach here.
\emph{Jayvee} currently has 32 evaluator operators.
The strategy pattern requires two additional classes per evaluator, one for the abstract class and one for the \emph{Polars} implementation.
This would increase the number of evaluator classes to 96.
Because of this, we considered implementing one additional method per evaluator the simpler option.
